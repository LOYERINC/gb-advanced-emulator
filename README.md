# GBA emulator learning project

This is a from-scratch learning project for a Game Boy Advance emulator. It can load ROMs, render several GBA graphics modes, run an expanding subset of ARM/Thumb instructions, advance approximate timer/display timing, handle IRQ dispatch, and persist SRAM/Flash/EEPROM saves. Direct Sound A/B and first-pass pulse, wave, and noise channels are mixed and played on Windows. It still does not run commercial games reliably: CPU coverage, BIOS services, sound accuracy, and hardware-accurate timing remain incomplete.

The project includes a tiny original homebrew ROM at `examples/gradient_demo.gba`. It turns on Mode 3 and writes a color pattern to all 38,400 screen pixels. To see it, run the desktop window below, choose **Open ROM…**, select that file, then press **Run**. This is an integration demo, not a commercial game.

See [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) for the step-by-step roadmap and completion criteria.

## Run the desktop window

By default, the emulator replaces a subset of common BIOS software calls itself and does not include Nintendo firmware. If you have a BIOS image you are entitled to use, click **Load BIOS…** and choose its 16 KiB file before loading a ROM. The image stays loaded for this app session; **Unload** returns to direct ROM boot and built-in replacements. With a user BIOS loaded, **Run** starts the CPU at the BIOS reset vector, so it attempts the normal firmware startup before entering the game. SWI instructions then enter Supervisor mode and execute the BIOS handler, which allows routines beyond the built-in subset to run. Generic undefined ARM opcodes and unsupported Thumb encodings enter the BIOS undefined-instruction vector; known instruction cases that this emulator has not implemented yet still pause with their address and opcode. After execution leaves BIOS, direct reads from the BIOS address range return a recent BIOS opcode instead of the BIOS contents; this open-bus value is approximate. Resetting or changing the BIOS restarts the current game and saves its `.sav` first. If BIOS startup stops at an unsupported instruction, unload the BIOS to return to direct boot. CPU/memory startup state and BIOS read protection are still approximations, so BIOS boot does not guarantee commercial-game compatibility.

The direct-to-ROM startup sets `POSTFLG` to its post-BIOS value so games can detect that boot has finished; when a user BIOS is loaded, the firmware performs that transition itself. The built-in BIOS `SoftReset` call clears CPU/BIOS reset state and jumps to `0x08000000`, or to `0x02000000` when the selection byte at `0x03007FFA` is nonzero. Without a BIOS, `HardReset` uses the same cartridge-reset path; it cannot replay the console's power-on animation. `RegisterRamReset` clears only the memory/device groups selected by its R0 flags; clearing IWRAM preserves its top `0x200` bytes for BIOS state. It forces the display blank during reset and leaves battery save data untouched. `Halt`, `CustomHalt` with R2 equal to `0`, and a direct write of `0` to HALTCNT pause CPU execution until an enabled/requested interrupt occurs; `CustomHalt` with R2 equal to `0x80` or a direct HALTCNT write with bit 7 set enters Stop. The emulator continues advancing display and timer hardware while halted, then wakes and services the interrupt when enabled by the CPU's interrupt controls. Stop freezes CPU, display, timer, and audio advancement until a keypad IRQ request wakes it; cartridge and serial wake sources are not implemented yet.

BIOS math calls `ArcTan` and `ArcTan2` accept signed 1.14 fixed-point inputs and return angles in GBA turn units; `GetBiosChecksum` returns the common GBA BIOS checksum value. `MidiKey2Freq` reads the base playback rate from a wave-data structure at `r0 + 4`, then uses the MIDI note in r1 and 8.8 fine tuning in r2 to calculate a playback rate. ArcTan results use Python's math functions, so they provide the intended angle but do not reproduce the original BIOS's small approximation errors exactly.

Common BIOS sound calls are recognized. `SoundDriverInit` creates a minimal SoundArea marker and pointer; the sound-driver main/mode/VSync, SoundGetJumpList, and MusicPlayerOpen/Start/Stop/Continue/FadeOut calls are stubs, so they let game code continue but do not play MPlay music. The emulator still has its separate first-pass PSG and Direct Sound output. `SoundChannelClear` stops those emulated channels. MultiBoot returns the documented failure result because link-cable transfer is not implemented.

Requires Python 3.10 or newer. On Windows, double-click [`Run GBA Emulator.bat`](Run%20GBA%20Emulator.bat) in this folder. From PowerShell, you can run:

```powershell
python emulator_app.py
```

You do not need a BIOS to start: without one, the emulator boots a ROM directly and uses its built-in replacements for some BIOS calls. The **Open ROM…**, **Run**, and **Load BIOS… (optional)** buttons stay pinned at the bottom of the right-hand panel, so they remain reachable even when the cartridge details need scrolling. To scroll those details, put the pointer over the right panel and use the mouse wheel or Page Up/Page Down. Click **Open ROM…**, browse to a `.gba`/`.agb` file or a `.zip` containing exactly one such ROM that you have the right to use, and click **Open**. ZIP files are read in place; the ROM is not extracted, and its `.sav` file is placed beside the ZIP. The game title, game code, version, ROM size, and save-memory detection appear in the **CARTRIDGE** panel. After the ROM loads, click **Run**. The app remembers the last ROM's file location and reloads it the next time the app opens; it does not remember the game-running state or copy the ROM. **Eject** clears that remembered location. The project does not include commercial games. The original `examples/gradient_demo.gba` is a tiny homebrew ROM that the emulator can execute to draw a Mode 3 color pattern. Other ROMs can still stop at CPU instructions or hardware features that are not implemented yet.

### Quick start without a BIOS

Think of the **ROM** as the game cartridge file. A **BIOS** is the GBA's built-in startup program; it is optional here, and the emulator does not include Nintendo's BIOS.

1. Click **Open ROM…** and pick a `.gba` or `.agb` game file you have the right to use. You can also pick a `.zip` that contains exactly one GBA ROM.
2. Check that the game's title appears in the **CARTRIDGE** panel.
3. Click **Run**. The game should begin; the keyboard controls are shown along the bottom of the window. For example, press the **arrow keys** to move, **Z** for A, **X** for B, and **Enter** for Start.

If the status changes to **Paused: unsupported instruction**, the emulator reached a CPU instruction it has not learned yet. The message shows the instruction's address and number; share those values to help identify what to implement next. For example, `0xE3C330DF` means `BIC r3, r3, #0xDF` (“clear these selected bits in register 3”); the emulator had mistakenly treated the number as another instruction, and its decoder has been corrected. A game title appearing in the window confirms the ROM was selected, but only seeing the game image change after **Run** confirms it is executing. Save data is stored in a `.sav` file beside the ROM (or beside the ZIP). When the emulator's Python source changes, close and reopen the desktop window to load the updated code; an already-open window keeps running its older copy.

To try the included demo, choose **Open ROM…**, open `examples/gradient_demo.gba` from this project folder, then click **Run**. The screen should fill with a color gradient. **Step CPU once** executes one supported instruction at a time; **Pause** stops a running game; **Reset game** starts the loaded ROM over from its entry point; **Eject** closes the current cartridge. For another ROM, repeat **Open ROM…** and select its file. Saves are written beside the ROM as a `.sav` file when you reset, eject, or close the emulator.

If the **Save memory** field says **Not identified**, this ROM has no recognized save-hardware marker. You can select a type from that field if you know the game's hardware: **SRAM · 32 KiB**, **Flash · 64 KiB**, **Flash 1M · 128 KiB**, or **EEPROM · auto size**. Changing the choice restarts the game from its entry point. If a `.sav` already exists, the emulator asks before reusing it because a different type can interpret or resize the existing data. Choosing the wrong type can prevent a game's saves from working; it does not change the ROM itself.

After loading a ROM, **Step CPU once** executes one supported instruction. **Run** executes batches until paused or until the CPU reaches a known instruction case that is not implemented yet. While running, the desktop redraws the game image up to 30 times per second to leave more time for CPU emulation. Keyboard mapping: arrows for directions, Z for A, X for B, Enter for Start, Backspace for Select, and A/S for L/R. KEYCNT can request IRQ 12 when selected buttons are pressed (in OR mode, any selected button; in AND mode, all selected buttons). Timer registers, scanline/VBlank/HBlank status, display IRQ request flags, and VBlank/HBlank DMA events advance. Direct Sound FIFO A/B and the four PSG channels (two pulse, wave, and noise) can generate stereo Windows audio output, preserving the GBA's left/right channel routing. Noise frequency uses the GBA polynomial-counter formula, though PSG output and mixing are still approximate. Enabled IRQ requests enter IRQ mode and pass through a small locally implemented BIOS-style dispatcher to the callback at `0x03007FFC`; ARM LDM/STM can transfer user-bank registers, and `LDM^` with PC can restore CPSR on exception return. Undefined-instruction exceptions enter an optional BIOS vector; FIQ, prefetch-abort, and data-abort entry are not yet implemented. No copyrighted BIOS image is included. ROMs marked `SRAM_V` save through 32 KiB SRAM; `FLASH_V`, `FLASH512_V`, and `FLASH1M_V` use emulated 64 or 128 KiB Flash; `EEPROM_V` uses the DMA3 serial protocol, with capacity selected from the command's address width. ROMs marked `SIIRTC_V` expose cartridge GPIO and a first-pass RTC that reports the computer's local date and time. Other GPIO devices such as sensors and rumble are not implemented. Saves are stored beside the ROM in a `.sav` file and flushed when you eject the game or close the emulator. The runner estimates instruction cycles, uses WAITCNT for Game Pak instruction fetches and data accesses, and adds basic wait estimates for EWRAM and 16-bit video memory, including one extra wait while palette/VRAM is being drawn. Game Pak prefetch and DMA bus timing remain unmodeled. Games may stop at unsupported instructions or hardware behavior.

The renderer applies WIN0/WIN1 layer clipping using each window's rectangle and WININ settings. When OBJ and OBJ-window are enabled, non-transparent OBJ-window sprite pixels select the high WINOUT settings; WIN0 and WIN1 take priority over that mask. It also applies first-pass GBA alpha blending, brightness increase/decrease, semi-transparent OBJ effects, and DISPCNT forced blank (solid white). BG mosaic works for tiled, affine, and bitmap backgrounds when the BG's mosaic bit is enabled; OBJ mosaic works for regular, affine, and OBJ-window sprites when their mosaic attribute is enabled. The MOSAIC register controls the horizontal and vertical block sizes. These are first-pass visual approximations, not cycle-accurate hardware emulation.

The CPU also models ARM7TDMI's unaligned data behavior for ARM and Thumb loads: unaligned word reads rotate the aligned word, odd unsigned-halfword reads rotate the aligned halfword, and odd signed-halfword reads act like signed-byte reads. The memory bus models a few GBA access-width quirks too: byte writes repeat into both bytes of BG VRAM and palette halfwords, byte writes to OBJ VRAM and OAM are ignored, and parallel SRAM/Flash accesses use an 8-bit bus even for CPU halfword/word operations. These details matter when game code reads packed data or uses byte stores and bulk-copy routines to update graphics and saves.

To inspect a ROM from the command line instead, run:

```powershell
python main.py path\to\your-own-game.gba
```

## Roadmap

1. Load a ROM and validate its header; the homebrew demo runs from its header branch through a full frame of VRAM writes.
2. Expand ARM7TDMI instructions, exceptions, and timing.
3. Improve scanline, interrupt, timer, and timed-DMA accuracy beyond the current first pass.
4. Add GBA sound channels and persistent save memory.
5. Improve video effects and test against more homebrew and CPU/video test ROMs.
